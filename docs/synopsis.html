4. Introduction and Background of the Study

Large Language Models produce plausible output but cannot reliably verify their own work. A widely studied response is multi-agent refinement: one agent produces a solution, another inspects or tests it, the feedback is returned, and the solution is revised. Systems such as Self-Refine, Reflexion and AgentCoder report improvements from this pattern, and frameworks such as ChatDev and MetaGPT extend it to role-specialised teams.

Two recent findings complicate that picture. First, Huang et al. (ICLR 2024) showed that without external feedback, self-correction does not improve results and frequently degrades them — implying that the verifier, not the critic, is the active ingredient. Second, budget-matched studies (Tran & Kiela, 2025) found that once the number of reasoning tokens is held equal, a single agent matches or exceeds multi-agent systems on reasoning tasks, concluding that reported multi-agent advantages are better explained by unaccounted computation than by architecture.

Meanwhile, a newer line of work proposes adaptive orchestration — selecting agents and workflow depth per task so that effort is spent only where it is needed. This project builds such a system and then applies to it the one test its own justification demands.

5. Objectives of the Project

  1. Design and implement an adaptive multi-agent system that accepts an unseen natural-language task at runtime, selects appropriate agent roles, generates a solution, validates it using executable tools, returns feedback, and refines iteratively under explicit budget limits.
  2. Implement independent validation using deterministic tools (program execution, query execution, answer matching) rather than relying on an LLM to judge its own output.
  3. Implement baseline conditions — including a budget-matched single agent — so that any observed benefit can be attributed to architecture rather than to extra computation.
  4. Construct a benchmark spanning three task families that differ in the strength of the available automatic verifier, and measure correctness, iterations, agents used, token usage, latency and cost.
  5. Provide a web interface that exposes the live execution trace, so that agent decisions, validation results and resource consumption are observable rather than hidden.

6. Problem Statement / Research Question

Adaptive multi-agent orchestration is justified on the grounds of computational efficiency — spending agents only when a task needs them. That is a claim about cost. Yet existing adaptive systems are evaluated against the strongest available baseline rather than against a single agent given an equal token budget, which is precisely the comparison that deflated earlier multi-agent claims.

Primary research question. Under a matched token budget, does adaptive multi-agent refinement improve task correctness over (a) a budget-matched single agent and (b) fixed multi-agent pipelines?

Secondary questions. (i) Does any observed benefit depend on the strength of the automatic verifier available for the task? (ii) Does combining tool-based validation with an LLM critic reduce undetected errors compared with LLM-only review? (iii) How many refinement iterations remain useful before further iterations stop paying for themselves?

The contribution claimed is a measurement and an evaluation methodology, not a novel architecture. Multi-agent collaboration and adaptive orchestration are both established prior art and are treated as such throughout.

7. Methodology / Approach

System. A task analyser classifies the incoming task; a planner emits a workflow specification selecting roles from a fixed library (generator, test designer, critic, repair); the orchestrator runs a bounded generate → validate → decide loop. Validation is performed first by deterministic tools and only then by an LLM critic, whose verdict is recorded but never treated as authoritative. For tasks supplied at runtime, a test-designer agent first derives executable tests from the task description.

Termination. The loop stops on acceptance, or on any of: maximum iterations, LLM calls, token budget, wall-clock limit, two iterations without score improvement, or a repeated identical output. Every termination reason is logged; unbounded loops are structurally impossible.

Evaluation. Five conditions are compared on a frozen benchmark:

ConditionDescription
ASingle agent, single attempt
A+Single agent given the same token budget as condition D, spent on repeated sampling with majority voting
BGenerator ↔ validator refinement loop
CFixed pipeline: generator → critic → repair
DARBITER — planner selects roles and iteration limit per task

All conditions share one engine and differ only by configuration, so differences cannot arise from implementation divergence. Every metric is computed from logged execution traces.

9. Expected Outcomes / Deliverables

  • A working adaptive multi-agent system that accepts unseen runtime tasks, performs real model calls, validates with executable tools, refines iteratively, and terminates under an explicit budget.
  • A web interface showing the live execution timeline, agent roles, validation results and resource consumption, with a replay mode for stored runs.
  • A frozen benchmark across three task families with differing verifier strength.
  • A comparative results table across the five conditions, reporting correctness alongside tokens consumed per task solved.
  • An analysis of failure modes classified using an established multi-agent failure taxonomy.
  • Reproducible experiment logs, a documented architecture, and a project report.

Expected findings are stated as hypotheses only and will be reported from measurement, whatever the outcome. We hypothesise that benefit tracks verifier strength — largest where executable tests exist and smallest where only a final answer can be checked — and that most improvement occurs within the first two refinement iterations. A result showing that adaptive orchestration does not outperform a budget-matched single agent would be a valid and reportable finding.
